# Архитектурные решения

## Отклонения от source.md

| № | Решение | Причина |
| :--- | :--- | :--- |
| 1 | Python-проект через uv, а не requirements.txt | Единый lock-файл, кэширование слоёв в Docker |
| 2 | OTel Collector пишет в otel_traces, Observer разбирает | Exporter clickhouse не умеет писать в произвольные таблицы |
| 3 | ReplacingMergeTree с updated_at, а не с наблюдением | Счётчики агрегируются перед вставкой |
| 4 | rule_proposals — ReplacingMergeTree | Обновление статуса без дублирования |
| 5 | SQL-правила переписаны с LEFT JOIN вместо коррелированного NOT EXISTS | ClickHouse не оптимизирует коррелированные подзапросы |
| 6 | Нет Kestra в первой версии | APScheduler достаточен для MVP |
| 7 | Нет эмбеддингов в agent_memory на MVP | Требует выбора модели, отложено на Этап H |
| 8 | .gitleaks.toml — allowlist для .env.example и тестов | Без него pre-commit блокирует коммит конфигов |
| 9 | Только MCP-сканирование, никаких локальных сканеров | Пользователь: «только MCP, только хардкор» |
| 11 | ClickHouse URL: формат `http://user:pass@host:8123/db` (не `clickhouse://`) | Rust bridge (с v1.109.0) парсит HTTP-URL напрямую |
| 12 | `/metrics` вынесен на порт 4001 через `PROMETHEUS_METRICS_PORT` | С v1.101.0 /metrics обслуживается отдельным процессом; на основном порту — 404 без callback prometheus |
| 13 | otel-collector — явный `command: ["--config", "/etc/otelcol/config.yaml"]` | Образ `otel/opentelemetry-collector-contrib` по умолчанию читает `/etc/otelcol-contrib/config.yaml` (дефолтный), наш конфиг не применялся |
| 14 | `make ch-ensure` вызывает `ensure_schema()` вручную через python | Rust bridge не вызывает `ensure_schema` при инициализации; без таблицы `spend_logs` insert падает с HTTP 404 |
| 15 | Для proxyapi/aitunnel провайдер задаётся префиксом `openai/` в `model` | По докам LiteLLM для OpenAI-compatible достаточно `openai/<model>` + `api_base`; `custom_llm_provider` не требуется |
| 16 | Observer пишет в `asset_proposals`, а не в `assets` | Права `agent_*` не включают INSERT на `assets` (только vector/otel); agent_writer имеет INSERT на `asset_proposals` |
| 17 | `rule_proposals`/`asset_proposals`: ORDER BY `(proposal_id)` вместо `(status, created_at)` | `(status, created_at)` схлопывал батч-вставки одной секунды (ReplacingMergeTree, FINAL терял строки) |
| 18 | Решение 2 не реализовано: OTel-экспорт в otel_traces отсутствует; LiteLLM пишет `litellm.spend_logs` напрямую, Observer читает её | Наблюдаемость на стенде: spend_logs — единственный реальный источник; отдельного пайплайна трасс нет |
| 19 | `AGENT_MODEL` в .env: `p/deepseek-v4-flash` (не `ollama/gemma4:26b`) | gemma4:26b не зарегистрирована в прокси; glm-4.7-flash отдаёт контент только в `reasoning_content`. В rule_engine добавлен фолбэк `content or reasoning_content` |
| 20 | sqlglot-Validator: select-only, whitelist `security_logs.*`/`system.*`, blacklist `file`/`url`/`s3`/`remote` и др. | AGENTS.md: весь SQL правил обязан проходить валидацию до попадания в `alert_rules`; проверка по AST, не по строке |
| 21 | Фоновый режим — только контейнер `agent-observer` с `serve` (APScheduler); задеплоено после 4 фиксов: CMD `agent run`→`/app/.venv/bin/agent serve`, `uv` не копировался в runtime-стадию, пароли передавались как `CLICKHOUSE_*_PASS` (конфиг читает alias `AGENT_*_PASS`), метрики 9101 не экспонировались | Контейнер не стартовал ни разу: `invalid choice: run`; без uv venv-бинарь `agent` работает напрямую; имена env в compose приведены к единому виду; `start_http_server(metrics_port)` добавлен в `serve` |
| 22 | Автопромоут активов `asset_proposals → assets` в гибридном режиме: `status='approved'` переносится всегда (ручное одобрение), `status='draft'` с `confidence >= 0.9` — автопилот; ниже порога — ждут `approved`. Перенос — INSERT в `assets` (ReplacingMergeTree сам схлопывает по `(asset_type, asset_key)`), затем proposal помечается `promoted` | Агенту запрещено писать в `assets` (AGENTS.md: права `agent_*` не расширять) — создан отдельный узкий пользователь `agent_asset_promoter` с единственным грантом `INSERT ON assets` (симметрично `agent_promoter` для правил). Полностью в атомате без новых прав невозможно: у ClickHouse нет триггеров, а `status` проставляется UPDATE-ом, на который MV не сработает |
| 23 | LiteLLM: `CLICKHOUSE_URL` обязателен и задаётся через compose (`http://default:${CLICKHOUSE_DEFAULT_PASS}@clickhouse:8123`); вариант «явные переменные» без URL нерабочий | В `rust_bridge.clickhouse.spend_storage_config` (main-latest) читается только `CLICKHOUSE_URL` (без него `ValueError`) и `CLICKHOUSE_DATABASE`; пароль берётся из URL. Просадка: контейнер litellm, поднятый со старым `CLICKHOUSE_URL`, даёт HTTP 401 в spend_logs после смены пароля default в `.env` — пересоздавать `docker compose up -d --force-recreate litellm` |
| 24 | `08_derived_views.sql`: `guardrail_mode` нормализуется `replaceRegexpOne('^\\["([^"]*)"\\]$', '\\1')` | LiteLLM пишет поле двумя форматами: строкой (`"pre_call"`, 3971 запись) и JSON-массивом (`["post_call"]`, 234 записи). `JSONExtractString` отдаёт сырой `["post_call"]`, `JSONExtractArrayRaw` — элемент с кавычками, JSONPath-индексы (`mode[0]`, `$[0]`) этой версией не поддерживаются (проверено на стенде) |
| 25 | Ручной бэкфилл витрин — только с `request_id NOT IN (SELECT request_id FROM <витрина>)` | MV наполняют витрины в момент вставки; повторный INSERT по тем же запросам даёт дубли (проверено: 98 строк extended при 95 в источнике). Шпаргалка — в шапке `08_derived_views.sql` |
| 26 | Дашборды Grafana генерируются `scripts/gen_dashboards.py` (stdlib) в `grafana/provisioning/dashboards/`; provider с `allowUiUpdates: true`, reload 30 s | JSON-дашборды руками трудно поддерживать; генератор даёт валидный JSON и позволяет пересобирать (правки в UI не затираются, но при регене перезаписываются) |
| 27 | UID датасорсов в provisioning = фактическим из БД Grafana (`PBFA97CFB590B2093`/`PDEE91DDB90597936`), а не «красивые» `prometheus`/`clickhouse` | Grafana 13.3 при смене UID у уже существующего провижиненого датасорса падает: `Datasource provisioning error: data source not found` (воспроизведено на стенде). UID в дашбордах должны совпадать с реальными, иначе панели не резолвятся |
| 28 | Фильтры переменных: single-select переменные со значением `'All'` в списке + `AND ('${var:raw}' = 'All' OR col = '${var:raw}')`; переменные собраны `SELECT 'All' AS v UNION ALL SELECT col ...` | Плагин `grafana-clickhouse-datasource` 4.23.3 НЕ поддерживает `$__conditionalAll` (макрос не раскрывается, проверено через `/api/ds/query`). Интерполяция переменных происходит на фронтенде Grafana до отправки запроса; `:raw` даёт значение без кавычек, кавычки — в SQL |
| 29 | Prometheus-бейджи в дашборде 1 — только фактически экспортируемые метрики (`agent_observer_runs_total`, `agent_correlator_incidents_total`, `agent_incidents_fp_ratio`, `agent_observer_assets_created_total`, `agent_observer_mcp_tools_created_total`, `agent_promoted_rules_total`, `agent_promoted_assets_total`, `agent_tools_without_declaration_total`) | `agent_active_rules`, `agent_gap_total`, `agent_assets_observed_total`, `agent_rule_engine_proposals_total`, `agent_validator_rejections_total` определены в `metrics.py`, но процесс `serve` их пока не экспортирует — бейджи были бы без данных. Когда агент начнёт их отдавать — добавить |
| 26 | Observer переключён с `litellm.spend_logs` на витрины `security_logs.*`: `spend_logs_extended` + `events_tool_calls` + `events_guardrails` | Витрины отдают вычисляемые поля (`tool_calls_count`, `guardrails_count`, `requester_ip`, `user_agent`, `trace_id`) без тяжёлой колонки `messages`; прямой доступ к источнику больше не нужен. Взаимно однозначно со старым чтением: `start_time→timestamp`, `user→user_id` (решение №24) |
| 27 | Новые типы активов `tool` (из `events_tool_calls.tool_name`) и `guardrail` (из `events_guardrails.guardrail_name`); задействована метрика `observer_mcp_tools_created` | План: инвентарь дополняется сущностями, которые коррелятор использует в правилах 05/08 (declared/observed bindings). Счётчик виден в Prometheus на 9101 |
| 28 | Правила коррелятора 06–10 (PII, action≠MASK, undeclared tool, tool burst, request failure) читают витрины `security_logs.*`, а не источник | Те же причины, что в №26; плюс `events_tool_calls`/`events_guardrails` позволяют анти-джоин по `mcp_tools`/`assets` без чтения `messages`. Правило 08 на стенде срабатывает всегда (пайплайн в `mcp_tools` не реализован) — это ожидаемо и задокументировано |
| 29 | Анти-джоин `LEFT JOIN ... AND right.key IS NULL` не работает в этой сборке ClickHouse (`join_use_nulls=0` по умолчанию) → правила 01/03/04/08 получили `SETTINGS join_use_nulls = 1` | Проверено на стенде: при пустой `mcp_tools` LEFT JOIN возвращает правые колонки как дефолтные значения, а не NULL (`countIf(tool_id IS NULL)` = 0 из 616 строк; `tool_id` = нулевой UUID). Без фикса правила молча никогда не срабатывали бы. Коррелятор исполняет текст правила как есть, `SETTINGS` проходит без изменений |
| 30 | LiteLLM подключён к Postgres (`litellm` БД) + включён встроенный Admin UI (`/ui`: логин `UI_USERNAME`/`UI_PASSWORD`) | Решение 21 («Без Postgres virtual keys не работают») устарело — для полноценного Admin UI (virtual keys, teams, budgets, CRUD моделей) нужна внутренняя SQL-БД прокси. Postgres в составе стека (13-й сервис), на хост не пробрасывается; новые переменные `.env`: `LITELLM_DB_PASS`, `LITELLM_UI_USERNAME`, `LITELLM_UI_PASSWORD` |
